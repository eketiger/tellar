technical handoff · v1

From prototype
to production.

Guía de implementación para convertir este prototipo en un producto real. El prototipo actual vive en el navegador: localStorage + IndexedDB, UI fiel al 100% de lo que tiene que construirse. Este handoff mapea cada pantalla a rutas, servicios, tablas y eventos sobre Next.js + NestJS + Prisma.

front · Next 15 · App Router api · NestJS 11 orm · Prisma 6 db · Postgres 16 + pgvector queue · BullMQ · Redis storage · S3 / R2 realtime · Socket.IO llm · Claude + OpenAI
01

Stack elegido (y por qué)

Pila "boring technology" — probada, contratable, y con toda la extensibilidad que el producto va a necesitar en los próximos 18 meses. Nada es experimental.

front-end

Next.js 15 App Router

Server Components para las pantallas pesadas (dashboard, analytics). Client Components para editor y viewer. Streaming para cargas largas.

— por qué: el editor necesita cliente rico (drag+drop, canvas), el dashboard necesita SSR con datos frescos. Next cubre los dos sin partir la app.

back-end

NestJS 11 modular

Un monolito modular por dominio: Auth, Workspaces, Tellers, Shares, Recordings, Agent, Events, Billing. Cada módulo con su controller + service + DTOs Zod.

— por qué: más fácil de contratar que Go/Rust, más ordenado que Express puro. Migramos a microservicios cuando duela, no antes.

datos

Prisma + Postgres

Prisma Client con types end-to-end. Postgres 16 + extensión pgvector para embeddings del agente. Row-level security opcional en fase 2.

— por qué: una sola base, RAG y eventos caben en Postgres perfectamente durante los primeros 2 años. Cero operaciones adicionales.

storage

S3 + CloudFront

Recordings (webm/mp4), PDFs de KB, avatares. Firmamos URLs por share, con TTL y watermark IDs embebidos.

queue + jobs

BullMQ + Redis

Jobs: transcode recordings, embed KB, aggregate analytics, send notificaciones. Exposed vía Bull-Board en /_admin.

realtime

Socket.IO + Redis adapter

Dashboard se suscribe a share:{id} y recibe eventos de view en vivo. Notificaciones push al creador cuando abren su deck.

// Skeleton de controller — todos siguen este patrón
import { Controller, Get, Post, Body, Param, UseGuards } from '@nestjs/common';
import { JwtGuard, WorkspaceGuard, Role } from '@/auth';
import { TellersService } from './tellers.service';
import { CreateTellerDto, UpdateTellerDto } from '@tellar/api-types';

@Controller('tellers')
@UseGuards(JwtGuard, WorkspaceGuard)
export class TellersController {
  constructor(private svc: TellersService) {}

  @Get()                                       // GET /tellers
  list(@CurrentWorkspace() ws) { return this.svc.list(ws.id); }

  @Post()                                      // POST /tellers
  @Role('EDITOR')
  create(@CurrentWorkspace() ws, @CurrentUser() u, @Body() dto: CreateTellerDto) {
    return this.svc.create({ workspaceId: ws.id, ownerId: u.id, ...dto });
  }

  @Get(':id')                                // GET /tellers/:id
  get(@Param('id') id: string) { return this.svc.findFull(id); }
}

07

Tiempo real & eventos

Cuando un inversor abre el deck, el creador debería verlo mientras pasa. Dos canales: eventos analíticos (escritura fire-and-forget) y un socket para el dashboard.

ingesta

Eventos desde el viewer

El viewer dispara slide_view, slide_dwell, agent_query y share_open con navigator.sendBeacon (sobrevive al cierre de pestaña). Batch de 5 o flush cada 3s.

La API los persiste en Postgres y re-emite en el canal ws:share:{shareId}.

entrega

WebSocket para el dashboard

El dashboard abre un Socket.IO a /ws, join al room share:{id}. Cada evento actualiza el funnel en vivo sin recargar.

Rate-limit 10 eventos/segundo por session para evitar abuse. Adapter Redis para escalar horizontal.

apps/api/src/modules/realtime/realtime.gateway.tsts
@WebSocketGateway({ namespace: '/ws', cors: { origin: process.env.WEB_ORIGIN } })
export class RealtimeGateway {
  @WebSocketServer() server!: Server;

  // Dashboard se suscribe a un share
  @SubscribeMessage('share:subscribe')
  async subscribe(@ConnectedSocket() s: Socket, @MessageBody() { shareId, jwt }) {
    const user = await this.auth.verify(jwt);
    const share = await this.shares.findIfOwner(shareId, user.id);
    if (!share) throw new WsException('forbidden');
    s.join(`share:${shareId}`);
  }

  // Llamado por EventsService cuando un viewer dispara un evento
  broadcast(shareId: string, event: ViewerEvent) {
    this.server.to(`share:${shareId}`).emit('event', event);
  }
}
08

Grabaciones: browser → S3 → stream

En el prototipo usamos IndexedDB. En producción, MediaRecorder → multipart upload a S3 con URL firmada → confirmación a la API → cola de transcode (ffmpeg) + transcript (Whisper).

01
Cliente pide upload URL
POST /recordings/upload-url devuelve un presigned URL por slide, con TTL de 15 min y content-type forzado a webm/mp4.
02
MediaRecorder chunked upload
5s chunks con multipart upload. Si se cae la red, reanuda del último chunk ACK. El creador ve progreso en vivo en el editor.
03
Confirmación + cola de transcode
POST /recordings encola job. Worker con ffmpeg normaliza a H.264/AAC 720p y genera thumbnails. Duración calculada desde el container.
04
Transcript con Whisper
Post-transcode, un segundo job saca transcript. Se indexa en KBChunks (embedding por slide de 30s) para que el agente cite el audio.
05
Stream al viewer por CloudFront
URL firmada por viewer + share. Cookie de CloudFront con watermarking ID embebido para poder probar filtraciones.
— DRM-liteTellar NO es Netflix. No hay Widevine. Lo que tenemos: watermark visible con el email, detección de DisplayCapture API para blackout, y streams firmados con TTL corto. Si alguien filtra el deck, el watermark nos dice quién. Es suficiente para early stage.
09

Agent RAG con citaciones reales

No es ChatGPT con un prompt. Es un pipeline chico de 4 pasos, con el LLM haciendo sólo la última parte. Todo citado, nada inventado.

step 1 · embed question

Question → vector

Usamos text-embedding-3-small (1536d). 8ms típico. Cacheado por hash de pregunta.

step 2 · retrieve

Top-k chunks del teller

pgvector con filtro por tellerId. Mezcla: 60% slides, 30% transcripts, 10% KB. k=8.

step 3 · rerank

Rerank con BM25

Re-score con Postgres FTS para compensar embeddings mediocres en dominios específicos. Top-4 sobrevive.

step 4 · answer

Claude Haiku + citas estrictas

System prompt: "Solo respondés con los chunks dados. Si no están, decís que no sabés y ofrecés escalar." Cada cita lleva slide idx o page.

apps/api/src/modules/agent/agent.service.tsts · skeleton
async ask({ tellerId, question, email }: AskInput) {
  const qVec = await this.embeddings.embed(question);

  // 1. retrieve — pgvector cosine similarity, filtrado por tenant
  const chunks = await this.prisma.$queryRaw<Chunk[]>`
    SELECT c.*, 1 - (c.embedding <=> ${qVec}::vector) AS score
    FROM "KBChunk" c
    JOIN "KBSource" s ON s.id = c."sourceId"
    WHERE s."tellerId" = ${tellerId}
    ORDER BY c.embedding <=> ${qVec}::vector
    LIMIT 8`;

  // 2. rerank con BM25 (Postgres FTS)
  const top = await this.rerank(question, chunks, 4);

  // 3. answer con Claude Haiku, strict cite
  const answer = await this.claude.stream({
    system: AGENT_SYSTEM,
    messages: [{ role: 'user', content: buildPrompt(question, top) }],
    maxTokens: 400,
  });

  // 4. log para analytics + usage counter
  await this.events.track({ type: 'AGENT_QUERY', tellerId, email, meta: { question } });
  await this.usage.increment(tellerId, 'agentQueries');

  return { answer, citations: top.map(c => ({ slideIdx: c.slideIdx, source: c.sourceName })) };
}
10

Auth & multi-tenant

Dos JWTs: uno para el creador (access+refresh, 15min/30d), y un share token corto para cada viewer autorizado. El tenant-ID viaja en el JWT y es la base del WorkspaceGuard.

creadores

JWT de sesión

Claims: uid, activeWs, role, plan. Firmado con asymétrica (ES256). Access de 15m + refresh rotativo guardado como httpOnly cookie.

  • Switch de workspace → nuevo access token con activeWs actualizado
  • Revocación por sesión (tabla Session con tokens hasheados)
  • OAuth con Google/GitHub vía Passport.js
viewers

Share token

Devuelto por /v/:slug/authorize luego de pasar el gate. Incluye shareId, viewerEmail, perms snapshot. TTL de 15 min, renovable mientras la sesión esté activa.

  • El viewer nunca ve JWT de creador
  • Revoke de share → blacklist por shareId en Redis (instant drop)
  • Watermark ID derivado del token, no del email (evita MITM)
